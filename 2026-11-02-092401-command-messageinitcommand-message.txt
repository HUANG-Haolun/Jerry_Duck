  It covers:
  - Layout: two robot packages exported from SolidWorks (MetalDuck, a 15-joint
    biped, and W01-00-000-0000, a 40-joint robot with two arms). Each has been
    converted into a ROS 2 Humble package. The packages in ros2_ws/src are links

      placeholders.

  - third_party/: a pointer to the upstream microduck and microduck_rl repos and
    their own agent docs. microduck_rl/AGENTS.md sets the sim-to-real rules
    (observation layout, joint order, how policies are exported to ONNX) that an
    RL port to MetalDuck would need to follow.

  microduck_rl 详解

  1. 这个项目是做什么的

  third_party/microduck_rl 是 Pollen Robotics 的 Microduck
  强化学习训练仓库。Microduck 是一个双足机器人，大约 25 cm 高、800 g 重，用 14
  个 Dynamixel XL330 舵机驱动。整条流程是：

  MJCF 模型 ──► mjlab 环境 (MuJoCo Warp, GPU 并行 4096 个环境)
            ──► PPO (rsl_rl) 训练，控制频率 50 Hz
            ──► 导出 ONNX（把观测归一化器一起烘进模型）
            ──► 发布到 HF Hub ──► 真机运行时 third_party/microduck 加载

  它依赖 mjlab==1.3.0、warp-lang、torch==2.9.1、better-actuator-models（BAM
  舵机模型）和 onnxruntime。Python 版本锁定在 3.12，必须用 uv 运行，训练需要
  CUDA GPU。

  2. 文件架构

  microduck_rl/
  ├── pyproject.toml          # 依赖；入口命令 train / publish / duck-body
  ├── AGENTS.md               # ★ 最重要的文档：命令、不变量、奖励设计经验
  ├── docs/                   # 各个策略的说明 + superpowers/ 下的设计 spec 和 
  plan
  ├── scripts/                # 命令行工具（导出、推理、sim2real 
  对比、拾取检测）
  ├── tests/                  # CPU 上就能跑的 cfg 不变量测试和 mdp 回归测试
  └── src/mjlab_microduck/
      ├── tasks/              # ★ 环境定义（核心）
      ├── robot/              # ★ 机器人模型（MJCF）和常量
      ├── actuator/           # BAM 舵机模型 + 摩擦域随机化 + 齿隙编码器
      ├── export.py           # checkpoint → ONNX，唯一合法的导出路径
      ├── publish/            # `uv run publish`：生成 manifest、校验、上传 HF 
  Hub
      ├── pickup/             # "被人拿起来"检测器，一个独立的小模型
      ├── sim/                # duck-body：把仿真身体通过 TCP 提供给真机的 
  robotd
      ├── train_cli.py        # `train` 命令（和 mjlab 的一样）
      ├── train_hook.py       # 拦截 --hf-jobs 参数，转到 Hugging Face Jobs 
  上训练
      └── hf_jobs.py

  2.1 tasks/：环境定义

  文件: __init__.py
  作用: 用 register_mjlab_task 注册所有任务 ID，包括 -Backlash- 齿隙变体（在
  _BACKLASH_TASKS 表里）
  ────────────────────────────────────────
  文件: mdp.py（约 7700 行）
  作用: 所有自定义的 MDP
  函数：奖励、事件/域随机化、观测、命令、课程。新增函数都写在这里
  ────────────────────────────────────────
  文件: microduck_velocity_env_cfg.py
  作用:
  主行走任务，同时也是其他任务共用的基础（机器人、域随机化、观测、命令、PPO
  配置）
  ────────────────────────────────────────
  文件: microduck_velstand / standup / sitstand / roulade / spin / ball_kick / 
  ground_pick_env_cfg.py
  作用: 各个技能任务：行走加站立、摔倒后起身、坐下站起、翻滚、转圈、踢球、捡东西
  ────────────────────────────────────────
  文件: microduck_velocity_rollers / swizzle / roller_crouch / roller_slope / 
  roller_standup_env_cfg.py
  作用: 脚上装轮子（轮滑版）的一系列任务
  ────────────────────────────────────────
  文件: backlash.py
  作用: 把任意一个环境配置包装成齿隙版本
  ────────────────────────────────────────
  文件: symmetry.py
  作用: 左右镜像数据增强。61 维观测的镜像表也在这里，默认关闭
  ────────────────────────────────────────
  文件: distill.py
  作用: PPO 加上从冻结专家策略做的行为克隆（DAgger
  风格），用来让学生策略学会起身
  ────────────────────────────────────────
  文件: slope_terrain.py
  作用: 斜坡地形

  注册的任务 ID 举例：Mjlab-Velocity-Flat-MicroDuck、Mjlab-StandUp-Flat-MicroDuc
  k、Mjlab-Velocity-Flat-Backlash-MicroDuck 等。用 uv run list-envs
  可以看到完整列表。

  2.2 robot/：机器人模型

  - microduck_constants.py：
    - 各个 XML 文件的路径，以及加载函数 get_walk_spec() 等。
    - HOME_FRAME：默认站姿的关节角，例如 hip_pitch ±0.4579、ankle 
      ±0.4530、neck_pitch 0.3491。动作就是相对这个姿态的偏移。
    - BAM 舵机参数：kp_fw=200；电池电压在 6.5 到 8.2 V
      之间随机，带负载压降；执行延迟为 3 到 6 个物理步。
    - 各种 EntityCfg，也就是"机器人模型 + 执行器 + 碰撞"的组合。
  - microduck/：从 Onshape 用 onshape-to-robot 导出的 MJCF。每种模型对应一个
    config_mjcf_*.json。碰撞配置分三类，每类都有一个 _backlash 齿隙孪生版：
    - robot_walk.xml：只有脚有碰撞，用于行走。
    - robot_groundcontact.xml：挑选出来的一组接地部件，用于起身、坐下等。
    - robot_allcollisions.xml：所有部件都有碰撞，舵机外壳命名为
      *_servo_collision。
    - 还有 robot_groundcontact_rollers.xml（轮滑版）、各种
      scene_*.xml（场景），以及 add_backlash.py（生成齿隙版 XML 的脚本）。
  - xl330_test_bench/：单个舵机的测试台模型，用来验证 BAM 模型。

  2.3 scripts/：常用脚本

  - export.py：导出 ONNX。
  - infer_policy.py：在 CPU 上用 MuJoCo 跑 ONNX，相当于上真机前的部署彩排。
  - testbench_sim2real.py、validate_bam_testbench.py、plot_observations_comparis
    on_plotly.py：对比仿真和真机。
  - pickup_*.py：拾取检测器的数据生成、训练、评估和演示。
  - play_latest.py、wandb_utils.py：wandb 相关的辅助工具。

  3. 模型结构

  3.1 策略网络（以行走任务 MicroduckRlCfg 为例）

  定义位置：src/mjlab_microduck/tasks/microduck_velocity_env_cfg.py:912

  Actor  : 61 维观测 → [归一化] → MLP 512-256-128 (ELU) → 14 维动作均值
           Gaussian 分布，标量 std，初始值 1.0
  Critic : 特权观测 → [归一化] → MLP 512-256-128 (ELU) → 1 维价值

  PPO 超参数：

  ┌────────────────────────┬────────────────────────────────────────┐
  │          参数          │                   值                   │
  ├────────────────────────┼────────────────────────────────────────┤
  │ lr                     │ 1e-3（adaptive 调度，desired_kl 0.01） │
  ├────────────────────────┼────────────────────────────────────────┤
  │ clip                   │ 0.2                                    │
  ├────────────────────────┼────────────────────────────────────────┤
  │ entropy                │ 0.01                                   │
  ├────────────────────────┼────────────────────────────────────────┤
  │ epochs / mini-batches  │ 5 / 4                                  │
  ├────────────────────────┼────────────────────────────────────────┤
  │ γ / λ                  │ 0.99 / 0.95                            │
  ├────────────────────────┼────────────────────────────────────────┤
  │ 每个环境每次迭代的步数 │ 24                                     │
  ├────────────────────────┼────────────────────────────────────────┤
  │ 最大迭代数             │ 50000                                  │
  ├────────────────────────┼────────────────────────────────────────┤
  │ 保存间隔               │ 每 250 次迭代                          │
  └────────────────────────┴────────────────────────────────────────┘

  其他任务各自定义自己的 RslRl...RunnerCfg，并使用不同的 experiment_name。

  3.2 Actor 观测：61 维，所有策略共用

  布局来自 tasks/symmetry.py：

  ┌───────┬──────────────────────────────────────────────────────────────────┐
  │ 下标  │                               内容                               │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 0:3   │ base_ang_vel，IMU 测得的角速度                                   │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 3:6   │ projected_gravity，机体坐标系下的重力方向                        │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 6:20  │ joint_pos_rel，14 个关节相对 HOME 的角度，带编码器偏置           │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 20:34 │ joint_vel_rel，14 个关节的速度                                   │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 34:48 │ last_action，上一步的动作                                        │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 48:51 │ 速度命令 [vx, vy, wz]                                            │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 51:55 │ 头部姿态命令（neck_pitch、head_pitch、head_yaw、head_roll        │
  │       │ 的增量）                                                         │
  ├───────┼──────────────────────────────────────────────────────────────────┤
  │ 55:61 │ 身体姿态命令 [x, y, z, roll, pitch, yaw] 的增量                  │
  └───────┴──────────────────────────────────────────────────────────────────┘

  14 个关节的顺序：

  - 0–4：左腿（hip_yaw、hip_roll、hip_pitch、knee、ankle）
  - 5–8：颈部和头部（neck_pitch、head_pitch、head_yaw、head_roll）
  - 9–13：右腿

  所有策略都用同一套 61
  维布局，这样真机上可以热切换策略。某个任务用不到的命令槽位要填零，但不能删掉。

  Critic 额外能看到特权信息，比如 base_lin_vel、无偏置的真实关节角、没有加 IMU
  安装误差的值。

  3.3 动作

  动作是 14 维关节位置目标：JointPositionActionCfg，scale=1.0，在 HOME
  姿态基础上加偏移。动作不做低通滤波。目标位置交给 BAM
  舵机模型（电压控制、摩擦随负载变化），它模拟的是舵机固件里的 PD 控制。

  3.4 Sim2real 措施（都在 velocity cfg 顶部和 mdp.py 里）

  - 域随机化：
    - 质心偏移 ±3 mm，通过课程逐步扩大。
    - 质量和惯量 ±5%。
    - 摩擦和电枢 ±10%。
    - 每 3 到 6 秒施加一次 ±0.3 m/s 的速度推力。
    - IMU 安装误差最多 6°。
    - 编码器偏置 ±0.015 rad。
  - 观测噪声和延迟：IMU 延迟 0 到 1 步，关节速度固定延迟 1 步，各项加均匀噪声。
  - 齿隙：齿隙变体在每个舵机关节上串联一个 ±1° 的被动铰链（命名为
    passive_*_backlash）。

  3.5 另一个小模型：拾取检测器

  位置：src/mjlab_microduck/pickup/model.py

  这是一个时序 CNN，约 2.5 万个参数。输入是最近 WINDOW 个时间步的 63
  维特征，输出是"机器人正被人拿着"的概率
  logit。真机用它来判断什么时候暂停或恢复策略。

  4. 模型文件在哪里

  仓库里没有任何 .onnx 或 .pt 文件，我搜过确认了。训练好的模型放在以下几个地方：

  ┌─────────────┬───────────────────────────────────────────────────────────┐
  │    内容     │                           位置                            │
  ├─────────────┼───────────────────────────────────────────────────────────┤
  │ 本地训练的  │ logs/rsl_rl/<experiment_name>/<日期时间>_<run_name>/model │

  ├─────────────┼───────────────────────────────────────────────────────────┤

  6. 移植到 MetalDuck 要注意的差异

  MetalDuck 的 URDF 有 15 个关节，比 Microduck 多一个
  mouth_joint，而且关节命名风格不同（left_hip_yaw_joint
  这种）。如果要复用这套训练框架：

  - 需要先把 URDF 转成 MJCF。
  - 在 robot/ 下新增模型和 constants。
  - mouth_joint 要么作为 passive_*
    被动关节处理，要么把观测和动作维度改掉。改维度就意味着放弃和现有 61
    维策略族的兼容。
  - URDF 里所有 effort 和 velocity 都是 0，需要补上真实值。
  - MetalDuck 用的舵机如果不是 XL330，BAM 的执行器参数也得重新标定。

  需要的话，我可以接着帮你规划 MetalDuck 的移植步骤。

  阶段 0：环境搭建（约半小时）

  curl -LsSf https://astral.sh/uv/install.sh | sh        # 装 uv
  cd ~/rl_control/third_party/microduck_rl
  uv sync                                               # 会按 pyproject 建 
  .venv，Python 3.12，不要用 conda 的 Python
  uv run python -c "import torch, warp; print(torch.__version__, 
  torch.cuda.is_available(), torch.cuda.get_device_name())"
  uv run list-envs
  uv run --with pytest pytest tests/                    # 这些测试只用 
  CPU，用来确认 cfg 的各项不变量没坏

  - 验收标准：cuda.is_available() 为 True，list-envs
    能列出所有任务，测试全部通过。
  - 5090 的注意点：它是 Blackwell 架构（sm_120），需要 torch 2.9.1 的 cu128
    wheel 和 warp 1.12 才能支持。如果 warp 报 kernel 编译错误，先怀疑这里。
  - wandb：训练默认把日志写到 wandb 项目 mjlab_microduck。可以先 uv run wandb 
    login，或者用 WANDB_MODE=offline 离线运行。是否能换成别的 logger
    我还没核实，跑起来时再看 --help。

  阶段 1：冒烟测试（几分钟）

  AGENTS.md 规定长时间训练之前必须先跑这一步：

  uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 64
  --agent.max_iterations 5
  uv run scripts/export.py Mjlab-Velocity-Flat-MicroDuck --checkpoint-file
  logs/rsl_rl/velocity/<run>/model_4.pt
  uv run scripts/infer_policy.py --walking output.onnx

  - 验收标准：训练不出 NaN，checkpoint 落盘，ONNX 能导出，infer_policy 能用 CPU
    版 MuJoCo 加载并运行，此时机器人摔倒是正常的。
  - 测吞吐：同样只跑 5 次迭代，分别用 1024、2048、4096
    个环境，记录每次迭代的耗时和显存占用，用来估算后面每个阶段要多少小时。

  阶段 2：主任务，行走（核心复现目标）

  uv run train Mjlab-Velocity-Flat-MicroDuck --env.scene.num-envs 4096
  --agent.max_iterations 4000

  - 预算：README 说 4096 个环境下 1 到 2 小时能得到可用步态；AGENTS.md

❯ 为什么这个模型结构如此简单，还有就是reward上限是什么                          

  Ran 6 shell commands (ctrl+o to expand)

● 我已经把每一项 reward 的公式和权重都核实过了，下面先讲为什么网络这么小，再讲
  reward 的上限。

  一、为什么模型结构这么简单

  Actor 是 61 → 512 → 256 → 128 → 14 的 MLP（ELU 激活），大约 20
  万参数。这在腿足机器人强化学习里是标准配置，不是偷懒。ANYmal、Unitree、Disney
  那些双足或四足机器人的 sim2real 工作，基本都用这个量级的网络。原因有五个：

  1. 任务本身的输入输出维度很低。 输入只有 61
     个数（IMU、关节角、关节速度、上一帧动作、命令），输出 14
     个关节目标角，没有图像，也没有长时间序列。它要学的是一个比较平滑的反馈控制
     律：观测到当前状态，就给出动作。几层 MLP 就足够逼近这样的映射。
  2. 性能瓶颈在数据和奖励，不在网络容量。 强化学习里，限制策略效果的通常是探索、
     奖励设计和仿真与真机之间的差距，而不是网络能不能表达。网络更大，PPO 往往更
     不稳定、训得更慢，学出来的步态也不一定更好。这个仓库真正花功夫的地方是
     mdp.py 里那 7700 行奖励函数、域随机化和课程设计，网络结构几乎没动过。
  3. 要部署到真机上实时运行。 策略在机器人自带的 RK3566（ARM A55 小核）上用 CPU
     跑，每 20 ms 就要推理一次（50 Hz）。20
     万参数一次推理只要零点几毫秒，网络大十倍就可能来不及。
  4. 小网络更不容易过拟合仿真。 网络大了，容易记住仿真器特有的漏洞，比如某种接触
     伪影，上真机后就失效。小网络再加上大量域随机化，泛化更稳。
  5. 为什么没有记忆模块（LSTM、观测历史）。 观测里已经放了 last_action，IMU
     也能直接测到姿态。速度这种需要从历史推断的量，被限制成只有 critic
     能看到的特权信息：critic 看真实速度，actor 看不到。这是非对称 actor-critic
     的标准做法。另外，观测加了随机延迟，关节编码器也加了偏置，这些都迫使策略对
     噪声更鲁棒，而不是依赖精确的状态。

  想加大网络或者加记忆，也只需要改 microduck_velocity_env_cfg.py:914 的
  hidden_dims。不过 AGENTS.md 里的经验是，先把奖励调对，比加大网络有用得多。

  二、reward 上限是多少

  wandb 上看到的数值是怎么算出来的

  mjlab 默认会把每一步的 reward 乘以控制周期 dt = 0.02 s。Episode_Reward/xxx
  的计算方法是：把一个 episode 里每一步的 原始值 × 权重 × dt 累加起来，再除以
  episode 时长 20 s。结果相当于**"平均每秒拿到的分数"**。

  所以每一项的理论上限是：原始值的上限 × 权重 × 0.02。

  这一组曲线显示的是课程学习的进度。训练开始时任务比较容易，随着迭代次数增加，训
  练程序会按预先写好的时间表逐步加难度。这些曲线记录的就是每项参数当前取的值。

  为什么要用课程

  一开始就把难度设满，机器人还不会走就要同时应付很强的扰动、很重的惩罚和很大的命
  令范围，最后往往学成"站着不动"。所以先让它在简单条件下学会走，再逐步加难度。

  注意一点：课程是按迭代次数切换的，不看策略学得好不好。到了指定的迭代，参数就会
  自动跳到下一档。

  上一条我写"XL330 是位置 PD 控制，你的舵机只有

  舵机模型（bam/actuator.py），里面写的是：

  duty_cycle = clip(error_gain · kp · (目标角 − 当前角), -max_pwm, max_pwm)

  可见 XL330 的固件也只用了 P，Microduck 用的参数是 kp_fw=200、D=0。所以"P 还是
  PD"不是两种舵机的区别。真正的区别在后面第三部分。

  一、P 和 D 是什么

  舵机内部就是一个小电机。固件每毫秒做一次"看误差、决定电机出多大力"，规则有这几
  种：

  项: P（比例）
  公式: 力 = Kp × (目标角 − 当前角)
  作用: 偏离目标越远，往回拉的力越大
  物理上像什么: 弹簧：拉得越开，回弹越狠
  ────────────────────────────────────────
  项: D（微分）
  公式: 力 = −Kd × 当前角速度
  作用: 转得越快，阻力越大
  物理上像什么: 阻尼器：像门上的闭门器、汽车减震
  ────────────────────────────────────────
  项: I（积分）
  公式: 力 = Ki × 误差的累积
  作用: 消除长期存在的小误差
  物理上像什么: 腿足机器人一般不用

  只有 P 的话，关节就像挂在弹簧上，到了目标位置会冲过头再弹回来，来回晃。加上 D
  以后，相当于给弹簧配了个减震器，能稳稳停住。

  二、XL330 只用 P 为什么不晃

  因为电机本身就自带阻尼。直流电机转起来时会产生反电动势，抵消一部分驱动电压。结
  果是转得越快，实际出力越小，效果和 D 项一样，这是物理特性，不需要固件去算。

  用 Microduck 模型里的参数算一下：kt = 0.366，R = 2.81 Ω，反电动势等效阻尼 =
  kt²/R ≈ 0.048 N·m·s/rad。它的备用 MuJoCo 模型里写的关节阻尼是
  damping="0.053"，两个数基本对得上。也就是说，仿真里用一个"阻尼"参数模拟的，正
  是电机这种天然的"D"。

  你的 UBT-12HC 也是直流电机，同样有这个天然阻尼。 所以"只有 P"本身不是问题。

  三、你的舵机和 XL330 真正的差别

  两者都是 P 控制，差别在 误差到 PWM 的映射曲线：

   PWM (电机出力)
    ^

     |  |
    0|__|__________________________> 位置误差

  ├────────────┼────────────────────────┼───────────────────────────────────┤
  │ 误差很小时 │ 出一点点力，越接近目标 │ 0.7° 以内完全不出力（死区）       │
  │            │ 越轻                   │                                   │

  │ 刚超出死区 │ 依然只出一点点力       │ 直接跳到约 19% 的力（最小 PWM 48  │
  │ 时         │                        │ / 255）                           │
  ├────────────┼────────────────────────┼───────────────────────────────────┤
  │ 整体手感   │ 平滑的弹簧             │ 先是一段空档，然后突然出力，有点  │
  │            │                        │ 像开关                            │
  └────────────┴────────────────────────┴───────────────────────────────────┘

  这对强化学习有两个影响：

  1. 站立和小幅调整会抖。 策略想把关节微调 1°，真机不是轻推一下，而是突然出一股
     力，容易冲过头，再反向冲回来，在目标附近来回抖。
  2. 仿真必须照着学。 MuJoCo 自带的执行器只会模拟平滑的弹簧加阻尼。如果仿真里用
     平滑执行器训练，上真机后舵机的行为和训练时不一样，策略就可能失效。这才是上

  四、所以我的建议仍然是改固件

● 对每个关节，你最后要得到这四个数：

  ┌───────────────┬─────────────────────────────────────────────────────────┐
  │     参数      │                          含义                           │
  ├───────────────┼─────────────────────────────────────────────────────────┤
  │ adc_zero      │ 关节处在 URDF 里 0 角度的姿态时，舵机读到的 ADC 值      │
  ├───────────────┼─────────────────────────────────────────────────────────┤
  │ sign          │ +1 或 -1：关节按 URDF 的正方向转动时，ADC               │
  │               │ 是增大还是减小                                          │
  ├───────────────┼─────────────────────────────────────────────────────────┤
  │ k             │ 每个 ADC 计数对应多少弧度（标称约 0.00614 rad，要实测） │
  ├───────────────┼─────────────────────────────────────────────────────────┤
  │ [lower,       │ 可用范围，用 URDF 角度表示                              │
  │ upper]        │                                                         │
  └───────────────┴─────────────────────────────────────────────────────────┘

  有了这四个数，主控就能在 ADC 和关节角之间来回换算：

  关节角(rad)   q   = sign × (adc − adc_zero) × k      ← 读传感器，喂给策略
  目标 ADC   adc_t = adc_zero + sign × q_target / k    ← 策略输出，发给舵机

  训练和推理都用 URDF 的角度，所以这四个数只要有一个错，策略在真机上就会出问题。

  ---

  准备：读位置时不能锁住关节

  舵机 ID 固定是 1，一次只能在总线上接一个舵机来标定。

  读位置要用 CMD 03（卸力）。文档写的是"每个合法命令都会触发一次位置 +
  速度应答"，所以一直发 03
  就能连续读到位置，电机始终不出力，你可以用手掰关节。PosH/PosL 填 0 即可。

  不要用 CMD 02 读位置。它会锁住当前位置并让电机出力，你就掰不动了。

  ---

  第 1 步：标定 k（换一种舵机时做一次就行）

  1. 拿一个舵机，输出轴上装一根长指针，或者把手机贴在舵盘上，用手机里的水平仪
     App 测角度。
  2. 卸力状态下记一个 ADC 读数，用手转动大约 90°，再记一个读数。
  3. k = 实际转过的角度(rad) / ADC 变化量。在不同位置多测几次取平均。

  如果测出来接近 0.35°/计数，说明 1024 个计数对应 360°；如果是 0.26°
  左右，说明电位器的有效行程只有约 270°。

  第 2 步：搞清楚 URDF 的 0 位长什么样

  conda activate ros_humble
  python view_urdf.py MetalDuck_description/urdf/MetalDuck_description.urdf

  所有滑条都在 0 时显示的姿态，就是 SolidWorks 导出时装配体的姿态，也就是 URDF
  的 0 位。截图保存，后面对着它摆真机。

  再把每个滑条往正方向拖一点，记下关节往哪边转，比如"左髋 pitch 正方向 =
  腿往后摆"。下面判断方向要用这份记录。

  第 3 步：逐个关节测量（机器人整机装好后做）

  对每个舵机重复下面几步：

  1. 接线：总线上只接这一个舵机，持续发 CMD 03 读 ADC。
  2. 找零位：用手把关节摆到和截图一样的姿态，记下
     adc_zero。尽量找可靠的参照，比如两个零件的边对齐、腿竖直向下，可以用直角尺
     或水平仪。这一步决定了零位的精度。
  3. 定方向：从零位开始，按第 2 步记录的正方向慢慢转。ADC 增大就是 sign = 
     +1，减小就是 sign = -1。
  4. 测范围：慢慢转到两端，遇到机械限位就停；如果先撞到其他零件或线缆，就停在撞
     到的位置。分别记下 adc_min 和 adc_max。
  5. 检查读数是否连续：在整个范围内来回慢慢转，ADC
     应该单调、平滑地变化。如果中间突然跳变，说明这段运动经过了电位器的盲区，要
     把舵盘拆下来转一个齿重新装，避开盲区。
  6. 检查固件窗口：固件会把目标值限制在 50–950 之内。如果 adc_min 小于 60，或者
     adc_max 大于 940，同样要把舵盘挪一个齿，让整个运动范围都落在窗口里。

  第 4 步：换算成 URDF 范围，并留出余量

  q_a = sign × (adc_min − adc_zero) × k
  q_b = sign × (adc_max − adc_zero) × k
  lower = min(q_a, q_b) + 余量
  upper = max(q_a, q_b) − 余量        余量建议 5° ≈ 0.087 rad

  把结果填进 URDF 的 <limit lower upper>，替换掉现在那些可疑的值，比如 hip_pitch
  的 [-3.4, 0.43]。

  第 5 步：记录下来

  建议每个关节写一行 YAML，部署时直接读这个文件：

  # calibration.yaml
  k: 0.00614            # rad / ADC count（实测值）
  joints:
    left_hip_yaw:   {adc_zero: 512, sign: +1, adc_min: 380, adc_max: 640}
    left_hip_roll:  {adc_zero: 498, sign: -1, adc_min: ...,  adc_max: ...}
    # ... 14 个关节

  以后只要拆装过舵盘，这个关节就要重新标定。

  第 6 步：通电验证

  先把机器人吊起来，让脚离地，然后一个关节一个关节地测：

  1. 从当前位置开始，用 CMD 01 发一个很小的目标变化，比如 +10° 对应的
     ADC。确认关节往 URDF 正方向转，并且转的角度对。
  2. 把所有关节发到 URDF 的 0 位，和第 2 步的截图对比。
  3. 左右对称检查：把仿真里的 HOME 姿态（比如左 hip_pitch = -0.46、右 =
     +0.46）分别发给左右腿，两条腿应该是镜像的。

  如果 sign 搞反了，舵机会朝相反方向全力转，很可能直接撞到限位。所以第一次发 CMD
  01 时，一定只发很小的变化量。
